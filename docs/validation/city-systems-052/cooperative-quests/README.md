# Совместные проекты: проверенный запуск

`native-results.json` фиксирует финальные JAR, 63 проверки на трёх последовательных JVM (33 + 15 + 15), хеши журналов и результаты чтения отдельных копий SQLite. После каждого завершения основная база содержит все четыре поставки и обе сметы. Перед следующим JVM совпадает SHA основной базы, отсутствуют WAL/SHM. Все четыре административные квитанции пережили остановку.

Стандартный путь проверки: `scripts/cooperative-quests-runtime-probe/{prepare,build,run}.py`. Для воспроизведения брать точные JAR из манифеста либо заново проверять все указанные версии. Режим `FAST_NATIVE_STOP` не вставляет диагностический SQL или дополнительный тик между последним подтверждением и штатной остановкой. Исходная база не открывается внешним SQLite-процессом: сначала копируются байты, анализируется только отдельная копия.

`stale-sidecar-forensics.json` и `pre-fix-fast-stop-checks.txt` сохраняют ранее неуспешную диагностику. Они **не являются результатом финальной сборки**. Проверенный TRUNCATE сам по себе не объяснил старое появление WAL между остановленным JVM и новым запуском. Причина старого поведения не установлена; в финальном последовательном сценарии оно не воспроизвелось. Файлы WAL при запуске никогда не удаляются автоматически.

Ограничения: реальная Folia/Towny и API аддонов, но игрок/окно/планировщик — явно заданные офлайн-заменители, а факт изъятия предметов — подготовленная подтверждённая поставка. Этот стенд не доказывает отображение сетевого клиента или работу стороннего банковского провайдера. Проверки старого инвентарного/денежного пути находятся в `ResourceDeliveriesSmoke` и остальных тестах Contracts.
