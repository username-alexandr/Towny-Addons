# Закупка материалов здания — Contracts 0.8.1

В 0.8.1 обычные контракты, опубликованные игроком или администратором-игроком, сохраняют его UUID в локальном платеже и запросе TreasuryPlus. Публикация из консоли остаётся системной. Старые квитанции без автора сохраняют прежнюю системную идентичность и не пересоздаются. Новые закупки материалов также сохраняют автора в локальном подтверждении публикации. Повторная проверка: 18 холодных программ, MunicipalTreasurySmoke41, Folia22+4+9; `validation/city-systems-052/procurement-actor`.

Мэр открывает `/t buildorders <здание>` (или `/townybuildorders <здание>`), выбирает недостающий материал и подтверждает точное количество, награду из казны и срок. `/townybuildorders mine` показывает сохранённые заявки; `status <UUID>` — квитанцию. Право `mintcontracts.buildorders` само по себе не заменяет проверку действующего мэра.

Сначала казна подтверждает резерв. Кнопка продолжения публикует оплаченный заказ в обычных городских контрактах. Поставка поступает в общий склад; принятые условия после оплаты не меняются при пополнении фонда здания. Существующие фонд здания и склад учитываются в расчёте, но не списываются при создании закупки. Активные и оплачиваемые поставки того же материала вычитаются из свободной потребности.

До публикации мэр может вернуть весь оплаченный резерв. После публикации используются прежние правила отмены городского контракта: полный возврат закупки уже недоступен. Смена мэра, удалённый проект или остановка модуля сохраняют оплаченный резерв. Новый действующий мэр явно продолжает публикацию либо возврат. Если банк сообщил неопределённый результат, автоматического повторного списания/зачисления нет; нужна сверка администратора в казне.

## API для меню и планировщика

`ru.neverland.mintcontracts.api.BuildingProcurementApi`, версия контракта 1; возможности `offers`, `quote`, `confirm`, `status`, `cancel`, `requests`. Все методы возвращают `CompletionStage` немедленно; их завершение вынесено за пределы `SuiteState`. Доступ к игроку и проверки полномочий выполняются через его entity scheduler и повторяются после подтверждения записи.

- `offers(Player, String project)` → список строк: `project`, `targetLevel`, `building`, `itemKey`, `name`, `amount`, `rewardCents`, `durationSeconds`, `reason`.
- `quote(Player, String project, String itemKey)` → неизменная смета, действующая 30 секунд.
- `confirm(Player, UUID request)` → подготовить оплату либо продолжить ранее подтверждённую закупку.
- `status(Player, UUID request)` → сверить существующие банковские квитанции без новой банковской операции.
- `cancel(Player, UUID request)` → отменить неоплаченную смету либо подготовить полный возврат неопубликованного резерва.
- `requests(Player, int page)` → заявки текущего города действующего мэра, 20 на страницу; страницы начинаются с 1.

Смета дополнительно содержит `requestId`, `town`, `townName`, `actor`, `actorName`, `createdAt`, `expiresAt`, `status`, `startedAt`, `detail`, `contractId`. Суммы передаются целыми копейками. UI использует полученный `itemKey` без самостоятельной сериализации предметов и не пишет чужие файлы, ресурсы или банковские счета. Статус доступен инициатору, текущему мэру города и администратору `mintcontracts.admin`; подтверждение и возврат — текущему мэру с правом закупок.

| Состояние | Значение |
| --- | --- |
| QUOTE | Смета ждёт явного подтверждения |
| FUNDING | Сохранено намерение; казна ещё не подтвердила точное списание |
| REVIEW | Банковский результат требует сверки; автоматического повтора нет |
| FUNDED | Оплата подтверждена; резерв ожидает решения действующего мэра |
| PUBLISHING | Сохранено намерение публикации с фиксированным сроком |
| PUBLISHED | Создан прежний городской контракт с тем же UUID |
| SETTLED | Городской контракт уже завершён или отменён своим механизмом |
| REJECTED / CANCELLED | Оплата отклонена / неоплаченная смета отменена |
| REFUNDING | Сохранены точный UUID и инициатор полного возврата; возможна ручная сверка |
| REFUNDED | Возврат подтверждён казной; публикация запрещена |

## Подключение и сохранность

Нужны Builds с `BuildingMaterialsApi.needs` и TreasuryPlus с `requestDebit`, `debitStatus`, `requestRefund`. При отсутствии новой казны закупки не создают платежей; старые городские контракты и публичные заказы продолжают свой жизненный цикл. Нового обязательного цикла зависимостей плагинов нет.

`procurement.sqlite` — отдельная база с одним ограниченным рабочим потоком, WAL/FULL, атомарными намерениями и административным outbox. Ошибка её открытия отключает только новые закупки. Существующие файлы контрактов, зданий и публичных заказов не заменяются. Перед обновлением остановить сервер и сохранить каталоги Contracts, Builds и TreasuryPlus целиком, включая возможные SQLite sidecar-файлы. Не удалять журналы или квитанции для повторного запуска оплаты.

Смета ограничена миллионом предметов и сроком 60–31 536 000 секунд. Пределы журнала: 100 000 заявок до проверенной архивации; одновременно действующие сметы — 16 на игрока, 64 на город, 2048 на сервер; незавершённые оплаты/возвраты — 8 на город и 256 на сервер. Очередь SQLite — 128. При достижении предела новые заявки отказываются до внешнего платежа. Оплаченные квитанции не удаляются по таймеру.

Используются существующие настройки `building-orders.enabled`, `default-unit-reward`, `unit-rewards.<MATERIAL>`, `maximum-reward`, `duration-seconds`. Отключение новых закупок сохраняет чтение квитанций и завершение принятых расчётов. Полная административная пауза модуля блокирует действия нейтрально до возобновления. Публичная эмиссия и шаблоны городских контрактов не менялись.

Казна принимает неизменный request UUID. Публикация независимо проверяет `PAID`, все условия исходного дебета и `backingAvailable=true`; исторического `PAID` после возврата недостаточно. Legacy RESERVE DONE создаётся вместе с активным контрактом без второго списания. Перед возвратом обязательно проверяется отсутствие durable-публикации. Аудит `CONTRACT_PAYMENT / PROCUREMENT_*` содержит исходный UUID, город, инициатора, сумму, время и направление возврата.

## Границы проверки

Проверки: Contracts 0.8.0 прошёл 18 холодных программ, включая `ProcurementSmoke` (29), `ProcurementAuditSmoke` (11) и `MunicipalTreasurySmoke` (30). Финальный native fixture на отдельном tmpfs прошёл Folia 26.2 в трёх последовательных JVM: 21 + 4 + 9 проверок, exit 0. Проверены действительная казна Towny, новые и обычные городские контракты, смена мэра, задержка, возврат, повреждённое дополнительное хранилище, перезапуск, физические снимки SQLite и закрытие при удержанном внешнем writer без блокировки Suite. Использованы явные заменители игрока/его scheduler и постоянного экономического адаптера; живой Vault, клиент и весь пак этим не проверены. Результаты: `docs/validation/city-systems-052/procurement`.

Предыдущий overlay-стенд дал аномалию служебных SQLite-файлов; её причина не установлена. Его свидетельства сохранены отдельно, финальные проверки не используют этот незавершённый сценарий.

## Обычные городские контракты

При установленном TreasuryPlus обычный городской контракт тоже сохраняет запрос резерва до обращения к банку. Пока казна не подтвердила оплату, контракт не принимает прогресс и его срок не расходуется. После точной квитанции PAID он продолжает работу; повтор использует тот же UUID. До подтверждения награда не считается оплаченной. Старые неопределённые PENDING-счета сохраняют ручную сверку и не превращаются в новый дебет. Временная занятость провайдера сохраняет запрос для следующей сверки, а не отключает все контракты.

Сам закупочный журнал и новый банковский gateway асинхронны. Публикация и последующая сдача материалов всё ещё используют прежний `ContractRepository` и муниципальный delivery/payment журнал. Их файловая запись остаётся синхронной; это явная граница миграции, а не утверждение о полностью асинхронном Contracts. В других аддонах отдельной миграции требуют прежние синхронные потребители Treasury `spend`; общий релиз до её завершения не готов.
