# NeverLandTownySuite 0.43.0 — ожидание общей блокировки на Folia

Дата: 26.10.2026. Chronicles 0.1.19, Control 0.4.14, Builds 0.8.35, Events 0.4.11. Полная матрица 40 аддонов — `versions.yml`.

## Что исправлено

В прежнем общем ядре каждый callback `SuiteScheduler` входил в Java-монитор `SuiteState`. Если другой поток держал его во время длительной операции, Global Region Scheduler или региональный поток ждал вместе с ним. Стек `Chronicles → SuiteState.run`, состояние `BLOCKED`, показывает ожидающий поток; он сам по себе не устанавливает, какой плагин держал монитор. Полного исходного дампа владельца для этого инцидента нет.

Теперь запланированные задачи пробуют занять общую блокировку без ожидания. Если она занята, задача переносится на следующий тик того же планировщика: global, region или entity. Работа с миром и сущностями не переезжает в произвольный фоновый поток. Повторяющаяся задача имеет только одно ожидающее продолжение; после выполнения выдерживается её период, накопленные пропущенные тики не исполняются лавиной. Отмена удаляет и отложенное продолжение. Очистка после исчезновения сущности выполняет только действия с учётными данными.

Синхронизация данных сохранена. Все вхождения старого монитора заменены на общий reentrant guard; JDK-объект блокировки един для изолированных загрузчиков всех JAR. Форматы сохранений, платежные квитанции и API аддонов не сбрасываются.

При проверке также обнаружено ожидание в обработчике загрузки чанка Camps. Сверка голограмм перенесена в региональную задачу с повторной проверкой загрузки чанка. Генерация раскопок Archaeology также перенесена в региональную задачу. Обработчики загрузки сущностей Events, Control и Logistics не ждут общую блокировку: работа с учётными данными откладывается, а непосредственная очистка читает только метки сущностей своего региона. Отложенная очистка курьера проверяет, что это всё ещё тот же NPC.

Chronicles дополнительно:

- Обходит города порциями: по умолчанию не более двух за тик, с проверкой бюджета 3 мс между городами.
- Считывает казну один раз на город и использует один снимок для всех денежных достижений.
- Проверяет готовность экономики перед получением Towny account. Если экономика недоступна, сохраняет прежнее наблюдение казны и не выдаёт денежные достижения по отсутствующим данным.
- Записывает автоматические сохранения истории в фоновом потоке; явное сохранение и остановка остаются с подтверждением записи.
- Ручная сверка сообщает, что поставлена в очередь. Ошибка при обработке одного города не оставляет завершённую задачу навсегда зарегистрированной как активную сверку.

Все предыдущие изменения исходной ветки сохранены, включая усиление рейдов по развитию города, чертежи строительства, сдачу материалов, историю операций и права городского совета. Клиентский CraftoUI этим пакетом не обновляется.

## Установка

1. Полностью остановите сервер. Сохраните резервную копию JAR и папок данных Towny и NeverLandTowny.
2. Для **каждого уже установленного** аддона NeverLandTowny замените старый JAR соответствующим файлом из этого пакета. Не оставляйте две версии одного плагина. Дополнительные неиспользуемые аддоны устанавливать не требуется.
3. Сохраните существующие конфигурации и игровые данные. Не заменяйте папки плагинов чистыми папками из примеров конфигурации.
4. Запустите сервер обычным полным запуском. Не используйте `/reload` или горячую перезагрузку JAR.
5. Проверьте загрузку всех ранее установленных модулей, затем `/nltlock` и обычные действия игроков. Экономический провайдер, Towny и остальные сторонние плагины остаются отдельными зависимостями.

**Нельзя заменить только Chronicles.** Протокол общего ядра изменён во всех 40 JAR. Новые модули проверяют установленные версии до своей загрузки данных. При смешении с прежним ядром они отключаются с сообщением «Несовместимые версии общего ядра». Это защита от параллельного доступа к данным через две разные блокировки. Замените оставшиеся старые JAR и снова полностью запустите сервер.

Для отката остановите сервер и верните весь предыдущий комплект JAR вместе. Сохранения не требуют конвертации; при восстановлении резервной копии данных учитывайте операции игроков, совершённые после её создания.

## Настройки и диагностика

В `NeverLandTownyChronicles/config.yml`, внутри существующего раздела `tracking`, можно добавить:

```yaml
tracking:
  towns-per-tick: 2
  scan-budget-millis: 3
```

Это значения по умолчанию и для старого файла без новых ключей. Допустимые пределы: 1–25 городов и 1–20 мс. Бюджет проверяется между городами: он не может прервать уже начавшийся медленный вызов стороннего API.

`/nltlock` — OP или `neverlandtownycontrol.admin`; доступна также из консоли. Показывает владельца общей блокировки, его текущий стек, длительность удержания и число отложенных попыток. Команда сама не захватывает эту блокировку. При удержании дольше секунды занятые задачи автоматически печатают такую диагностику, не чаще одного сообщения за 10 секунд на весь комплект. Счётчик показывает попытки переноса, а не число потерянных задач.

## Границы исправления

Устранено блокирующее ожидание общей блокировки в запланированных callback `SuiteScheduler`. Прямые синхронные вызовы API, обработчики событий и команды продолжают использовать взаимное исключение и могут ждать. Длительная работа внутри уже начатого callback также не прерывается. Медленный диск, внешний экономический провайдер или другой плагин по-прежнему могут вызывать отдельные задержки. Эта сборка не доказывает, кто удерживал монитор в присланном инциденте; для этого нужен полный watchdog/thread dump.

Проверки и их точные результаты находятся в `docs/validation/ledger-0.43.0/`. Проверка без подключённых игроков не заменяет плейтест под нагрузкой, проверку конкретного экономического провайдера и всех игровых сценариев.
