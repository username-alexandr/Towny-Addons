# TreasuryPlus 0.3.0: подтверждаемые бюджетные операции

Состояние: банковский gateway проверен отдельно; **полный комплект пока нельзя выпускать**. Старый `spend(...)` без ID теперь возвращает `false` до создания заявки и до обращения к банку. Перед общим выпуском все существующие вызывающие аддоны должны перейти на UUID и асинхронное подтверждение. `canSpend(...)` — только предварительная проверка сохранённого бюджета, а не обещание оплаты. Нельзя включать fallback на прямое списание, если Treasury отказал или занят.

Новые лицензии Research здесь ещё не реализованы. Gateway подготовлен как обязательная основа для них и муниципальных закупок Contracts.

## Контракт API v1

Добавлены capability `requestDebit`, `debitStatus`, `requestRefund`, `refundStatus`. Существующие данные городов, доли, отчёты и прежние pending-счета сохраняются. `async-debits` и `flow-gap` — дополнительные поля прежней схемы; повреждённая или неизвестная схема не перезаписывается.

```java
CompletionStage<Map<String,Object>> requestDebit(
    UUID operation, UUID town, String category, String source,
    long cents, String reason, UUID actor, String ownerPlugin);
Map<String,Object> debitStatus(UUID operation);
CompletionStage<Map<String,Object>> requestRefund(
    UUID refundOperation, UUID paidDebitOperation,
    UUID actor, String ownerPlugin, String reason);
Map<String,Object> refundStatus(UUID operation);
```

Суммы заданы целыми сотыми монеты. Категории: `construction`, `army`, `infrastructure`, `social`, `free`. Максимум одной заявки — 100 000 000 000 сотых; `source` до 64 символов `[a-z0-9_/-]`, имя аддона до 64 `[A-Za-z0-9_-]`, причина до 384 символов без перевода строки. Нулевые/отрицательные/некорректные суммы отклоняются.

Future запроса подтверждает сохранение `PREPARED` либо возвращает ранее сохранённую квитанцию. Это **ещё не разрешение выдавать товар или запускать проект**. Клиент читает immutable snapshot через `debitStatus`. Нужно проверять одновременно `status`, исходный ID и весь зафиксированный payload. Несовпадение любого из полей при повторном UUID отклоняется даже для ранее оплаченной квитанции.

| Статус | Значение для вызывающего аддона |
| --- | --- |
| ABSENT | Сохранённой заявки ещё нет. Разрешён повтор того же точного запроса. |
| PREPARED | Намерение и резерв статьи подтверждены записью. Банк пока не подтверждён. |
| INVOKING | Вызов банка мог произойти. После рестарта переводится в REVIEW без повторного списания. |
| PAID | Точное банковское наблюдение и изменение бюджета подтверждены записью либо администратор сверил конкретную квитанцию. |
| REJECTED | Банк не вызывался или администратор подтвердил отсутствие операции. Нельзя выдавать результат. |
| REVIEW | Ответ неоднозначен. Удерживается резерв, автоматического повтора банка нет. |

Основные поля: `operation`, `town`, `category`, `source`, `cents`, `reason`, `actor`, `owner`, `status`, `createdAt`, `changedAt`, `review`, `kind`, `backingDebit`, `audited`. UUID представлены строками, суммы и даты — `long`, `kind` — `DEBIT` или `REFUND`.

Для DEBIT доступны `backingAvailable`, `refundedCents`, `refundOperation`. Перед публикацией ещё не распределённого escrow потребитель заново требует `PAID` и `backingAvailable=true`. Историческое `PAID` не исчезает после возврата и само по себе не доказывает наличие обеспечения сейчас.

Возврат всегда равен полному оплаченному исходному списанию, возвращается в тот же город и исходную статью. Сумму возврата нельзя передать произвольно. Совпадают город, категория, источник, владелец и обеспечение; новый UUID, актор и причина фиксируются отдельно. На одно списание допускается один незавершённый или оплаченный возврат. Неоднозначный возврат также требует REVIEW, а не повторного пополнения банка.

**Обязанность владельца escrow:** разрешать `requestRefund` только пока средства не распределены получателям. Treasury проверяет своё обеспечение, но не может узнать, выдал ли вызывающий аддон товар или выплатил деньги стороннему получателю. Нужен собственный durable intent/ACK и блокировка конкурирующих publish/cancel у потребителя.

## Запись, Folia и остановка

- Сканирование городов, банковские потоки, изменение долей, ручная сверка и новые квитанции используют один bounded `DurableSnapshots` writer. Файл, сериализация YAML и fsync не выполняются под общей Suite-блокировкой.
- Снимок публикуется только после ACK записи. При ошибке записи предыдущий снимок остаётся видимым, новые расходы закрываются. Архив квитанций не удаляется и не допускает повторного использования UUID; предел 50 000 записей останавливает новые заявки.
- Сканирование обрабатывает до 64 городов за ход, поток — до 512 событий за сохранение. Очередность scan / gateway / flow не даёт постоянным внешним поступлениям остановить уже принятую заявку другого города.
- Observer содержит только ограниченный immutable снимок события. Буфер — 4096 событий, причина — максимум 1024 символа. Суммы ожидающих приходов/расходов доступны без линейного обхода. При переполнении фиксируется `flow-gap`, выплаты закрываются, разрыв переживает рестарт. Очистка очереди не снимает разрыв автоматически.
- Проверка доступной статьи учитывает ещё не сохранённые исходящие события. Возврат проверяет допустимость будущего учтённого и фактического баланса до обращения к банку.
- Вызов Towny Account выполняется на Global Region без ожидания общего Suite guard. Дальнейшее подтверждение результата выполняется рабочим потоком. Если сервер остановился после банка, результат всё равно сохраняется. Повторный stop возвращает ту же цепочку завершения.
- Вызов `onDisable` под уже удерживаемым внешним Suite guard не ждёт файловую очередь; отложенное завершение диагностируется отдельно. Старые записи не заменяются пустым файлом при неудачной загрузке.
- Административная пауза Treasury или аддона-владельца не запускает PREPARED в банк. Recovery-only перевод INVOKING→REVIEW работает и при сохранённом `flow-gap`.
- Загрузка конфигурации и экспорт CSV выполняются вне общего guard; игроку сообщается об успешном изменении бюджета только после ACK.

`flow-gap` нельзя снимать просто по текущему балансу: он не восстанавливает распределение расходов по статьям и историю. Нужна проверка банковского журнала и восстановление данных при остановленном сервере. Не удаляйте pending-счета или архив UUID для обхода этой защиты.

## Административная сверка

Право `neverlandtownytreasury.admin` или OP для нового меню:

- `/townytreasury requests` — список квитанций, REVIEW первыми;
- `/townytreasury request <UUID>` — город, сумма, источник, владелец и причина;
- `/townytreasury resolve-request <UUID> paid|unpaid confirm` — решение по одной проверенной квитанции.

В меню нужны выбор результата и отдельное подтверждение. Перед подтверждением повторно проверяются права, состояние REVIEW и версия квитанции. Банковская операция не запускается повторно. Прежний `resolve` не может изменить async-квитанцию.

Аудит: `TREASURY_ASYNC_DEBIT`, `TREASURY_ASYNC_REFUND`, `TREASURY_ASYNC_REVIEW`. Пишется собственным bounded worker вне Suite; статус незаписанного аудита хранится в квитанции, ошибка аудита не вызывает повтор банка. Control должен подписать эти категории в единой админ-панели; его файлы в этой работе не менялись.

## Проверка

Точный JAR: `638a665b8f53347786d68aa5f115a627c6a186c5c34d0fe2d0d39de7f6dff578`.

Cold: 5 программ — AsyncBudgetPersistenceSmoke 25 проверок, BankFlowsSmoke 9, ForecastSmoke 11, TreasuryAccessSmoke, TreasurySmoke с 10 000 смешанных операций и DebitSmoke. Проверены delayed physical ACK, невыдача неоплаченного снимка, повреждённая база, точный UUID/payload, budget/refund conservation, reverse pending validation, bounded observer buffer, UTC и прежние отчёты.

Native: два полных запуска Folia 26.2 с Towny 0.103.2.0 и Control 0.6.1, **20 + 8 проверок**, оба JVM exit 0. Реальные Treasury state machine, журнал и Towny Account/Observer. Подтверждены physical ACK, пауза владельца, непрерывный поток другого города, бюджетный предел, повтор ID, обеспеченный возврат, неизвестные ответы без replay, явная сверка, реальный onDisable под внешним guard, сохранение результата после shutdown и полный рестарт. Recovery при gap содержит явно описанный crash-boundary seed.

Экономический backend в native fixture заменён управляемым EconomyAdapter. Это не проверка конкретной сборки Vault/Essentials и не тест сетевого клиента или кликов GUI. Первая fixture завершилась из-за reflection в probe, подтянувшего отсутствующую optional PlaceholderAPI; исправлен только probe. Production JAR во второй fixture не менялся.

Доказательства: `docs/validation/city-systems-052/treasury-async/`, воспроизводимая fixture — `scripts/treasury-async-runtime-probe/`. Независимый read-only review закрыл найденные блокировки, starvation, ошибочную связь pending, переполнение возврата и гонку индекса обеспечения. Общий релиз остаётся закрыт до миграции legacy callers и проверки полного совместимого комплекта.
