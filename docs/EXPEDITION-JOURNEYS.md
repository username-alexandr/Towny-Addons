# Поэтапные экспедиции — NeverLandTownyExpeditions 0.2.0

В `/expedition` игрок выбирает шаблон, затем порядок прохождения и отдельно подтверждает условия. Обычная экспедиция остаётся доступной; `/expedition start <id>` сохраняет обычный режим.

Новые варианты:

- **Разведка → зачистка:** сначала найти все цели; до завершения разведки враги похода не наносят и не получают урон. После подтверждения последней цели начинается бой.
- **Зачистка → поиск:** сначала победить всех врагов площадки; поиск целей открывается после последнего подтверждённого убийства.

Состав группы, цели, враги, материалы, цена припасов, исходная награда и длительность шаблона сохраняются вместе с выбранным вариантом. Изменение или удаление шаблона после начала не меняет принятую экспедицию. Бонус лагеря/города к длительности применяется при создании экземпляра, после чего его срок сохраняется обычным таймером.

Роль «разведчик» или «защитник» выбирается добровольно в меню активного похода. Она не запрещает другие действия и не увеличивает награду. История каждого действия хранит роль на момент его совершения. Можно проходить поход без роли.

В новом режиме личная награда требует хотя бы одного подтверждённого действия: найти цель площадки или победить её врага. Простое присутствие не даёт награду. Один игрок может пройти оба этапа. Действия посторонних игроков, повторное взаимодействие с той же целью и повторный UUID врага не увеличивают вклад. Число врагов и целей ограничено исходным шаблоном; дополнительные награды не создаются. Старые экземпляры без признака `planned` продолжают прежнее одновременное прохождение и прежние правила награждения участников.

## Хранение и остановка

- `data.yml` сохраняет прежнюю схему 2 и старые данные. Дополнительные поля `planned`, `site-ready`, `setup-note`, `generated` читаются как необязательные.
- `journeys.yml` — отдельный журнал новых вариантов: зафиксированные условия, роли, вклад и ожидающие квитанции административного аудита.
- `reward-effects.yml` сохраняет прежнюю схему 1 и идентификаторы наград. Намерение `PENDING` обязательно записывается до внешней выдачи; неизвестный результат не повторяется автоматически.
- `return-tickets.yml` сохраняет прежний формат. Одновременные выдачи прав на возврат проходят последовательную очередь.

Собственные чтения и записи этих файлов выполняются отдельными ограниченными рабочими очередями. Под общей блокировкой снимается только образ состояния. Выдача предметов работает в потоке игрока; `saveData()` вызывается без общей блокировки, после чего отдельный работник проверяет точную квитанцию в реальном файле игрока. Неудачная или неподтверждённая выдача остаётся для сверки администратора.

При повреждении `journeys.yml` новые поэтапные походы останавливаются без поражения; обычные экспедиции продолжают работать. Повреждённый файл не заменяется пустым. При `journeys.enabled: false` поэтапные походы ставятся на паузу без штрафа. После восстановления журнала или включения настройки администратор проверяет состояние и возобновляет таймер через штатное админское управление задачами. Нейтральная отмена остаётся доступной.

Административные записи имеют категорию `EXPEDITION_PLAN`: создание условий, добровольная роль, подтверждённый вклад и итог. Квитанция сначала сохраняется вместе с изменением похода, затем добавляется в аудит с неизменным ID; после подтверждения удаляется из исходящей очереди. Повтор после рестарта не создаёт вторую запись.

## Площадка и припасы

Новый снимок местности сохраняется до установки площадки. Перед установкой проверяется, что мир ещё совпадает со снимком. Снятие припасов не повторяется автоматически после неизвестного результата. Прерванная подготовка остаётся на паузе с пояснением для администратора.

Для новых площадок сохраняются ожидаемые установленные блоки. При завершении восстанавливаются только они или уже собранные цели; посторонние изменения сохраняются и требуют ручной проверки. При недоступном мире исходный снимок сохраняется. Старые площадки без `generated` читаются по прежним правилам.

**Ограничение внешнего API:** существующий Camps API v1 `consume()` сам выполняет синхронную запись схрона внутри общей блокировки и не принимает ID операции. Обновление Expeditions не может устранить внутреннее ожидание другого плагина. Неизвестное списание останавливает запуск для ручной сверки; автоматического повтора и заявления о транзакционной атомарности между плагинами нет. Обновление этого API — отдельная работа.

## Пределы первой версии

Журнал новых походов: до 512 экземпляров, до 64 участников в каждом, до 512 подтверждений вклада, до 1024 исходящих квитанций, файл до 32 МиБ. При заполнении новые изменения закрываются без удаления истории; требуется проверенный административный архив с резервной копией. Цели, накладывающиеся друг на друга при построении площадки, не допускаются в новый режим.

Основной файл ограничен 64 МиБ. Реестр эффектов — 100 000 записей; незавершённые намерения при очистке не удаляются. Очередь выдачи — до 64 игроков, очередь проверки файла игрока — 4 задания, очередь возвратов — 128 запросов и до 16 384 действующих билетов. Очередь записи основного файла — 32 снимка. Переполнение останавливает соответствующее изменение с сохранением предыдущих данных.

## Установка

1. Остановить сервер и сохранить копии папок Expeditions и Camps, а также миров и данных игроков.
2. Удалить прежний JAR Expeditions и установить единственный `NeverLandTownyExpeditions-0.2.0.jar`.
3. Сохранить существующие YAML. Новая настройка `journeys.enabled` по умолчанию включена; новые записи добавляются без удаления старых наград и истории.
4. Запустить сервер. Проверить обычную экспедицию, новый вариант через меню и наличие категории экспедиций в административном аудите.

Права сохранены: `mintexpeditions.use`, `mintexpeditions.start`, `mintexpeditions.admin`. Ручной возврат по-прежнему требует `neverlandtownyexpeditions.return`.

Холодная сборка на закреплённых зависимостях Folia 26.2: 8 исполняемых программ. Среди них проверка двух порядков и идемпотентного вклада (19), сохранения/аудита/повтора/повреждения журнала (12), асинхронных намерений и параллельных возвратов (13), прежних выплат и миграции наград (12).

Реальный Folia 26.2 build 7 (`14b7fee`), Java 25.0.5: **22 + 10 + 6 проверок в трёх отдельных JVM, все exit 0**. Площадка, враги, события блоков/смертей, журнал, нативный инвентарь/PDC и фактический player.dat использованы без подмены. Два варианта завершены по порядку; ровно две награды по 2 алмаза пережили перезапуск без повтора. Сохранены прежний прогресс и старая денежная награда. Проверена пауза нового режима и повреждение дополнительного журнала при работающем основном реестре. После трёх запусков аудит содержит ровно 13 уникальных квитанций.

Стенд использует реальные CraftPlayer/ServerPlayer без сетевого входа и заранее выбранную площадку. Данные Towny resident созданы стендом; разрушение в тестовой wilderness разрешено явно. Индекс сущностей проверяется после перечисления owning chunk — как в штатном guard площадки. Старт с физическим списанием схрона Camps и реальный экономический провайдер этим испытанием не сертифицированы. Сетевая проверка полного маршрута игрока остаётся отдельным плейтестом.
