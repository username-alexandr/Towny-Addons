# Личные заявки рынка

Личный рынок позволяет игроку заранее указать, сколько обычных ресурсов он хочет купить или продать и по какой цене. Город для этого не нужен. Деньги покупателя и товары продавца резервируются до появления подходящей встречной заявки: неподтверждённая заявка не участвует в торговле.

Это отдельный раздел `NeverLandTownyMarket`. Существующие местный и международный городские рынки, их предложения, покупки и файл `market-data.yml` сохраняются. Команда `/orders` относится к публичным заданиям Contracts и к личному рынку отношения не имеет.

## Что доступно игроку

| Команда | Действие |
| --- | --- |
| `/townymarket personal` | Открыть свои заявки |
| `/townymarket personal book` | Посмотреть открытые заявки всех игроков |
| `/townymarket personal pickup` | Открыть получение товаров |
| `/townymarket personal mine 2` | Открыть вторую страницу своих заявок |
| `/townymarket limit-buy OAK_LOG 64 10.50` | Подготовить покупку 64 дубовых брёвен по цене не выше 10,50 за штуку |
| `/townymarket limit-sell OAK_LOG 64 10.50` | Подготовить продажу 64 дубовых брёвен по цене не ниже 10,50 за штуку |
| `/townymarket limit-confirm <UUID подтверждения>` | Подтвердить подготовленную заявку; обычно используется кнопка подтверждения |
| `/townymarket limit-cancel <UUID заявки>` | Отменить неисполненный остаток своей заявки |
| `/townymarket limit-cash` | Перечислить доступные деньги рынка на личный счёт |
| `/townymarket limit-items OAK_LOG 64` | Получить 64 дубовых бревна из личного раздела получения |

Алиас основной команды — `/nltmarket`. Цена указывается за один предмет, с точкой или запятой, не более двух знаков после разделителя. Подтверждение действительно 60 секунд. В окне подтверждения показаны количество, цена и полный резерв. Пока игрок не подтвердил заявку, деньги и предметы не перемещаются.

При покупке резервируется вся максимальная стоимость заявки на личном счёте Towny. При продаже весь указанный товар забирается из обычных ячеек инвентаря. Если предметов недостаточно, частичного изъятия нет. Предметы из второй руки, экипировка и содержимое вложенных контейнеров для резерва не используются.

Деньги после продажи, возвращённый денежный резерв и экономия покупателя попадают в раздел получения. Купленные товары и остаток отменённой продажи также сначала попадают в раздел получения. Они не выбрасываются на землю при заполненном инвентаре. Кнопка товара предлагает получить до 64 предметов; командой можно запросить другое количество в пределах допустимой партии. Если для всей запрошенной партии нет места, выдача не начинается.

Отмена возвращает только неисполненный остаток. Уже завершённые сделки не отменяются. Повторная отмена той же заявки не создаёт второго возврата.

## Допустимые товары и доступ

Личный рынок принимает только материалы из `personal-orders.materials` и только обычные предметы, совпадающие с новым ванильным предметом этого материала. Предметы с собственным именем, чарами, описанием, дополнительными данными, содержимым или другими отличающимися свойствами не принимаются. Благодаря этому одинаковый код материала не превращает разные ценные предметы в один обезличенный товар.

Игрок может торговать без города и без городского здания рынка. Требуются режим выживания или приключения, права `neverlandtownymarket.use` и `neverlandtownymarket.personal`; оба права по умолчанию доступны всем. Доступ администратора к сверке задаёт `neverlandtownymarket.admin`, по умолчанию доступный OP.

Для денежных операций требуется работающая экономика Towny с подключённым провайдером и существующая запись игрока в Towny. Установка одного Vault не доказывает, что провайдер экономики подключён. При недоступной экономике новая покупка и получение денег не выполняются.

Пример выдачи прав через LuckPerms:

```text
lp group default permission set neverlandtownymarket.use true
lp group default permission set neverlandtownymarket.personal true
lp group admin permission set neverlandtownymarket.admin true
```

## Как выбирается встречная заявка

Заявки одного игрока между собой не исполняются. Сопоставляются только подтверждённые покупки и продажи одного материала, когда максимальная цена покупателя не ниже минимальной цены продавца.

Сначала рассматриваются покупки с большей ценой. Для них выбираются продажи с меньшей ценой. При одинаковой цене приоритет имеет более ранняя заявка; при одинаковом времени используется UUID, чтобы результат оставался определённым после перезапуска. Цена сделки равна цене более ранней из двух встретившихся заявок.

Например, продавец раньше выставил 40 брёвен по 8 монет. Затем покупатель создал заявку на 64 бревна по 10 монет и внёс 640 монет в резерв. Первая сделка передаст покупателю 40 брёвен, продавцу — 320 монет, а покупателю вернёт 80 монет разницы цены. Для оставшихся 24 брёвен останется резерв 240 монет. Если более ранней была покупка по 10 монет, встречная продажа по 8 исполнится по 10.

Возможны частичные исполнения и исполнение одной заявки несколькими игроками. Сопоставление работает без присутствия владельцев в игре; получение товаров и перечисление денег требуют входа владельца. За один проход, запускаемый раз в секунду, создаётся не более 20 сделок.

Сделка переводит только ранее зарезервированные деньги и предметы. Система не выдаёт серверную награду и не создаёт валюту.

## Настройка и ограничения

Настройка находится в `plugins/NeverLandTownyMarket/config.yml`:

```yaml
personal-orders:
  enabled: true
  materials: [STONE, COBBLESTONE, OAK_LOG, SPRUCE_LOG, BIRCH_LOG, SAND, GLASS, IRON_INGOT, COPPER_INGOT, GOLD_INGOT, COAL, WHEAT]
```

После изменения конфигурации используется `/townymarket reload`. Пустой список материалов заменяется встроенным списком выше; для остановки создания заявок следует устанавливать `enabled: false`. Неверный материал или неверный тип значения `enabled` приостанавливает создание личных заявок. Максимум в списке — 256 материалов.

| Ограничение | Значение |
| --- | --- |
| Действующие и ожидающие подтверждения заявки одного игрока | 32 |
| Количество в одной заявке или одной выдаче | 1–3456 предметов |
| Минимальная цена предмета | 0,01 монеты |
| Максимальная полная стоимость одной заявки | 1 000 000 000 монет |
| Одно перечисление денег из раздела получения | До 1 000 000 000 монет |
| Всего сохранённых заявок | 5000, включая завершённые |
| Квитанции в основном файле | До 20 000; старые завершённые выдачи переносятся в архив |
| Недавние завершённые выдачи в основном файле | После превышения 1024 сохраняются последние 512 |
| Всего сохранённых исполнений | 20 000 |
| Размер файла личного рынка | До 32 МиБ |
| Одновременно подготовленные подтверждения на сервере | До 1024; одно на игрока |

Цены и остатки внутри журнала хранятся целым числом сотых долей монеты. Ограничения количества, стоимости и объёма журнала заданы в коде, а не отдельными параметрами YAML.

`personal-orders.enabled: false` останавливает создание и автоматическое исполнение личных заявок. Общий `enabled: false` также останавливает новые личные сделки. Само по себе такое выключение не сжигает резерв: отмена остатка и получение ранее накопленного остаются разрешёнными. Это не относится к полной выгрузке плагина, аварийной заморозке модуля, ошибке хранилища, незавершённой операции владельца или исчерпанию журнала выдачи — в этих случаях необходима проверка администратора.

Удаление материала из списка запрещает новые заявки на него, но не удаляет прежние заявки и товары. Существующие заявки могут продолжить исполняться, пока личный рынок включён; отмена и получение прежнего товара остаются допустимыми.

**Ограничение эксплуатации текущего журнала:** завершённые выдачи автоматически архивируются, но заявки и исполнения не удаляются. Предел 5000 заявок останавливает создание новых; предел 20 000 исполнений останавливает сопоставление. Открытый остаток можно отменить и получить при исправных хранилище, экономике и сохранении игрока. Если основной файл всё же достиг предела квитанций или размера, архив недоступен либо исход внешней операции неизвестен, новые внешние действия останавливаются с сохранением резерва до проверки. Безусловной выдачи при любой ошибке хранения система не обещает. Повышение лимитов произвольным редактированием файла и удаление истории не являются процедурой обслуживания; автоматического архивирования заявок и исполнений пока нет.

## Хранение и перезапуск

Личные заявки хранятся отдельно в `plugins/NeverLandTownyMarket/personal-orders.yml`, схема 2. Схема 1 загружается без потери данных и при следующем подтверждённом сохранении переводится в схему 2. Файл содержит заявки, квитанции резервирования и недавних выдач, доступные деньги, товары к получению, исполнения и накопленные итоги архивных выдач. Существующий `market-data.yml` не преобразуется в этот формат и не заменяется.

Завершённые квитанции получения денег и предметов переносятся в `plugins/NeverLandTownyMarket/personal-orders-claims/`. Каждая неизменяемая часть архива содержит исходные UUID, результаты и ссылку на предыдущую часть; имя включает номер и SHA-256 содержимого. Сначала подтверждается запись части архива и её каталогов, затем основного файла с накопленными выплатами по каждому владельцу. До подтверждения основного файла квитанции не исчезают из видимого состояния. После сбоя лишняя часть, на которую основной файл ещё не ссылается, не используется как подтверждение выплаты.

Все квитанции резервирования и все `PENDING` сохраняются в основном файле. Архивируются только завершённые выдачи, включая проверенные отказы. Накопленные итоги денег и предметов участвуют в проверке сохранности имущества каждого владельца. Старый UUID остаётся в архиве и не может создать новую выдачу. При запуске проверяются цепочка архива, суммы, получатели и отсутствие повторов; чтение выполняется в отдельном рабочем потоке, пока личный рынок показывает состояние загрузки. Повреждение или отсутствие связанной части архива останавливает личный рынок.

Архив занимает дополнительное место на диске и не удаляется автоматически. Резервная копия должна включать основной файл и **весь** каталог архива. Нельзя переносить только `personal-orders.yml`, удалять старые части или независимо восстанавливать их из разных моментов времени. Поиск отдельной старой квитанции ограничен 4096 частями за запрос; превышение выдаёт ошибку необходимости отдельной проверки, а не результат «квитанции нет».

Перед внешним списанием, забором или выдачей создаётся квитанция `PENDING`. Операция с банком или инвентарём начинается только после подтверждения записи этой квитанции на диск. Внутренняя сделка сохраняет изменения обоих владельцев одним состоянием: частично опубликованной передачи между двумя кошельками не предусмотрено.

Банк сверяется по уведомлению счёта с идентификатором операции. Если провайдер сообщил отказ без уведомления, дополнительно проверяется, что баланс не изменился. Изменившийся или недостоверный баланс при таком ответе означает неизвестный результат и оставляет `PENDING`. Один только изменившийся баланс не считается доказательством успешной операции.

Для предметов планируется полное новое содержимое инвентаря без частичного изъятия или частичной выдачи. На потоке игрока устанавливаются инвентарь и метка `neverlandtownymarket:personal_market_receipt`, затем вызывается сохранение игрока. Возврат из `saveData()` сам по себе не считается подтверждением: отдельный рабочий поток проверяет метку в фактическом файле игрока `.dat`. До успешной проверки квитанция рынка не становится `DONE`. Если расположение сохранения не удалось определить до изменения инвентаря, перемещение предметов не выполняется. Ошибка после изменения требует сверки.

После перезапуска `PENDING` не повторяется автоматически. Это намеренная остановка при неизвестном исходе: банк или сохранение игрока могли завершиться перед падением сервера, а журнал рынка мог не успеть получить результат. Пока у владельца есть такая квитанция, новые личные операции владельца блокируются до завершения или сверки. Другие игроки продолжают работать при исправном журнале.

При загрузке проверяется соответствие резервов, исполнений, получателей и остатков денег и товаров. Повреждённый файл не заменяется пустым. Ошибка личного журнала приостанавливает личные заявки, а существующий городской рынок имеет отдельное хранилище.

## Сверка администратором

Личные операции и исполнения записываются в общий аудит с категорией `MARKET_DEAL`. Снимки сторон захватываются под короткой блокировкой, запись выполняется отдельным ограниченным исполнителем без удержания `SuiteState`; при переполнении или ошибке выводится `AUDIT GAP`. Очередь дописывается при штатной остановке. Основным источником финансового состояния остаётся журнал личного рынка: ошибка дополнительного аудита не повторяет денежную операцию. Для конкретной операции используйте UUID квитанции. Для банка в причине операции передаётся точный маркер `[personal-market:UUID]`.

```text
/townymarket limit-inspect
/townymarket limit-inspect <UUID квитанции>
/townymarket limit-resolve <UUID квитанции> applied confirm
/townymarket limit-resolve <UUID квитанции> not-applied confirm
```

Первая команда выводит до 50 ожидающих квитанций. Вторая показывает владельца, вид операции, товар, количество, сумму и состояние конкретной квитанции, включая архивную. Чтение архива выполняется без задержки потока игрока; во время записи может потребоваться повторить запрос через секунду. `limit-resolve` доступна также из консоли с правом администратора; она сверяет остановленную квитанцию, а не повторяет банковскую операцию или выдачу предметов.

| Вид квитанции | Что означает `applied` | Что означает `not-applied` |
| --- | --- | --- |
| `BUY_FUND` | Полная сумма действительно списана с личного счёта; заявка допускается к исполнению | Деньги не списаны; заявка отменяется без возврата несуществующего списания |
| `SELL_STOCK` | Весь товар действительно забран и результат сохранён; заявка допускается к исполнению | Товар не забран; заявка отменяется без дополнительной выдачи |
| `CASH_CLAIM` | Деньги действительно перечислены на личный счёт; выдача закрывается | Перечисления не было; сумма снова доступна в разделе получения |
| `ITEM_CLAIM` | Предметы действительно получены и результат сохранён; выдача закрывается | Выдачи не было; товары снова доступны в разделе получения |

Перед выбором результата проверьте журнал провайдера экономики по UUID, точную сумму и направление либо сохранённую метку игрока вместе с инвентарём и обстоятельствами операции. Общая разница баланса после других платежей, отсутствие сообщения в чате или слова игрока не определяют результат однозначно. Текущая метка игрока хранит последнее такое перемещение; её отсутствие в отдельно восстановленном или заменённом сохранении не доказывает отказ операции.

Если результата нельзя установить, оставьте `PENDING` и сохраните файлы и банковские журналы для разбирательства. Нельзя выбирать `not-applied` только для снятия блокировки: уже прошедшая выдача тогда снова окажется доступна. Нельзя выбирать `applied` без доказательств: это может признать отсутствующий резерв или закрыть невыданное имущество. Решение по уже закрытой квитанции не меняется повторной командой.

Журнал предотвращает автоматический повтор неизвестной операции, но не делает сторонний банк и файл рынка одной общей транзакцией. Обещание безусловного «ровно один раз» через произвольного экономического провайдера здесь не даётся. Ручная сверка требуется именно там, где внешнее подтверждение отсутствует.

## Установка и проверка

Остановите сервер штатно, сохраните резервную копию каталога плагина, данных игроков и экономики, затем замените JAR, оставив единственную версию `NeverLandTownyMarket` в `plugins`. Существующие городские данные не удаляйте. Новый личный журнал создаётся отдельно при первом сохранении; при обновлении его и каталог `personal-orders-claims` нужно сохранять вместе с остальными данными. Автоматического истечения заявок, уничтожения невостребованных ресурсов или удаления истории по возрасту нет. Перенос завершённых выдач в архив сохраняет их историю, а не стирает её.

Проверка кода включает чистую модель резервов, сопоставления и сверки: сохранение денег и товаров по каждому владельцу, частичные сделки, цену более ранней заявки, запрет сделок с собой, повторные запросы, отмену и неизвестные исходы. Наличие таких проверок не заменяет запуск конкретной сборки на сервере.

Перед вводом в эксплуатацию на копии сервера Folia проверьте игрока без города, покупку и продажу между разными игроками, частичное исполнение, заполненный инвентарь, отключение личного рынка, недоступный банк и перезапуск с `PENDING`. Отдельно проверьте чтение метки из реального файла игрока на используемой сборке Folia и сверку обоих направлений банковских операций. Эта инструкция описывает реализованный протокол; сама по себе она не является отчётом об успешном испытании на рабочем сервере.


## Результаты проверки сборки 0.2.0

29 октября 2026 года сборка прошла пять программ проверки: прежний городской рынок, модель личных заявок (152 проверки и 32 659 случайных переходов), сохранение и архивирование (37 проверок), проверка файлов игроков (16 проверок), неблокирующая очередь аудита (7 проверок). На Folia 26.2 с Towny 0.103.2.0 отдельный стенд прошёл 22 проверки при первом запуске и 11 после полного перезапуска JVM. Отчёт с контрольными суммами JAR и всеми утверждениями: [`validated-0.2.0.json`](../scripts/personal-market-runtime-probe/validated-0.2.0.json).

В стенде использовались настоящие `ServerPlayer`/`CraftPlayer`, инвентари, постоянные данные, `saveData()`/`loadData()` и файлы игроков. Отключение сохранения данных игрока проверено для приёма и выдачи предметов: молчаливый возврат из ванильного сохранения оставлял квитанцию ожидающей сверки. Подтверждённые инвентари восстановились после перезапуска, а несохранённый приём не стал обеспеченной продажей. После перезапуска проверено сохранение последней записи аудита, дописанной при остановке. Также проверены перенос 1025 старых квитанций в архив, остаток 975 сотых монеты, частичная сделка, отмена остатка, получение при выключенном создании заявок и сверка без повторной выплаты.

Онлайн-статус, интерфейс инвентаря и планировщик тестового игрока были заменены явными прокси, а банк — контролируемым счётом. Проверка реального подключённого клиента и производственного экономического провайдера этим стендом не заявляется.
