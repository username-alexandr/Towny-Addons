# Серверный склад и строительные заказы — Suite 0.44.0

Contracts 0.4.0, Control 0.4.16. Остальные модули совпадают с 0.43.2. Матрица версий — `versions.yml`.

## Что получают игроки

В `/orders` добавлены 150 поставок по 30 видам стройматериалов; всего в каталоге 230 заказов. В каждой новой группе представлены все пять редкостей. Древесина: дуб, ель, берёза, тропическая, акация, тёмный дуб, мангровая, вишня, бледный дуб, бамбуковые блоки, багровые и искажённые стебли. Строительные блоки: камень, булыжник, колотый глубинный сланец, андезит, диорит, гранит, туф, кальцит, чернит, базальт, песок, красный песок, гравий, глина, стекло, кирпичные, кварцевые блоки и призмарин.

Это **сбор и передача настоящих предметов**, а не подсчёт ломания дерева или камня. Ресурсы из обычного инвентаря передаются на серверный склад, затем серверная награда направляется на личный счёт. Именные и изменённые предметы не принимаются. Для новой сдачи нужен режим выживания. Рыбалка и охота в транспорте из предыдущего обновления сохранены.

Примеры начального баланса (формат: количество / награда в монетах):

| Редкость | Дубовые брёвна | Булыжник | Кварцевые блоки |
|---|---|---|---|
| Обычный | 64 / 80 | 128 / 80 | 16 / 100 |
| Необычный | 128 / 180 | 256 / 180 | 32 / 250 |
| Редкий | 384 / 550 | 512 / 450 | 64 / 600 |
| Эпический | 1024 / 1400 | 1024 / 1000 | 128 / 1300 |
| Легендарный | 2048 / 2700 | 2048 / 2200 | 256 / 2700 |

Полный список — `SERVER-MATERIALS-CATALOG-0.44.0.csv`, источник условий — `modules/NeverLandTownyContracts/src/main/resources/orders.yml`. Количества новых заказов помещаются в обычный инвентарь. Условия можно менять в конфигурации.

## Хранение и безопасность передачи

SQLite-файл: `plugins/NeverLandTownyContracts/server-materials.db`. Хранятся ID заказа, UUID и имя игрока на момент сдачи, шаблон, материал, количество, редкость, награда, даты и состояние передачи. Остатки и резервы строек находятся в этой же базе. Драйвер включён в Paper/Folia; отдельный сервер базы или новый плагин не нужен.

Порядок новой сдачи:

1. В фоновом потоке сохраняется неизменяемая заявка. На этом этапе предметы ещё у игрока, запас не увеличен.
2. В регионе игрока повторно проверяются заказ, инвентарь, права, состояние модуля, экономика и лимит. Создаётся удержанная денежная квитанция.
3. Предметы списываются ровно один раз. Сохранение игрока подтверждает передачу и специальную квитанцию.
4. Транзакция SQLite одновременно подтверждает поставку и увеличивает запас. Повторный ID не создаёт повторное пополнение.
5. Только после этого денежная квитанция передаётся обычной очереди выплат. База и журнал выплат сохраняют возможность завершить этот шаг после перезапуска.

Если результат сохранения игрока неизвестен, автоматического повторного списания нет. Выплата остаётся удержанной до подтверждения квитанции при входе или административной сверки. Ошибка/повреждение базы останавливает новые публичные заказы и их таймеры; файлы не заменяются пустыми. Уже подтверждённые данные не исчезают из-за повторного нажатия, выхода или остановки.

Вся работа SQLite выполняется отдельным ограниченным фоновым потоком; региональные задачи не ждут результата через `join()`/`get()`. Для базы используются WAL и `synchronous=FULL`. Основание выбора — официальные документы Paper о встроенном драйвере и SQLite о долговечности транзакций:
https://docs.papermc.io/paper/dev/using-databases/
https://www.sqlite.org/pragma.html#pragma_synchronous

## Администрация

`/nltadmin` → **Серверные выплаты** → **Серверный склад**. Прямой вход: `/orders admin resources`.

| Команда | Назначение |
|---|---|
| `/orders admin resources balance` | Получено и доступно по каждому материалу |
| `/orders admin resources history [страница]` | Игроки, заказы, количества и состояния сдач |
| `/orders admin resources allocations [страница]` | Резервы под конкретные стройки |
| `/orders admin resources export` | CSV всех заявок и сдач, включая спорные состояния |

Игровые меню открываются только администратору; в консоли выводятся текстовые страницы. CSV находится в `plugins/NeverLandTownyContracts/resource-exports/`.

Пример резерва под спавн:

```
/orders admin resources allocate spawn OAK_LOG 256 confirm Дуб для постройки ворот спавна
```

Команда выдаст ID резерва. Он уменьшает доступный запас, но не выдаёт физические предметы и не размещает блоки. Завершение учёта:

```
/orders admin resources consume <ID> confirm Ворота спавна построены
/orders admin resources return <ID> confirm Стройка отменена материалы не использованы
```

Используется одно решение: израсходовать резерв **либо** вернуть его. Повтор одинакового решения не меняет остаток второй раз; использованный резерв вернуть нельзя. В истории остаются автор и основание. Это учёт для будущих строек; автоматическое размещение спавна подключается строительной интеграцией через API ниже.

Просмотр: `neverland.orders.resources`. Изменения резервов: дополнительно `neverland.orders.resources.manage`. OP и `neverland.orders.admin` имеют оба доступа; полный административный пермишен Control наследует их через `neverland.orders.admin`. Игрокам достаточно прежнего `neverland.orders.use`.

Сверка спорной сдачи сохраняет знакомые команды:

```
/orders admin show <ID заказа>
/orders admin resolve <ID заказа> taken confirm Передача инвентаря проверена ресурсы списаны
/orders admin resolve <ID заказа> untouched confirm Инвентарь проверен ресурсы остались у игрока
```

Новая поставка проходит сначала через решение в SQLite, затем через денежную квитанцию. `taken` подтверждает запас и выпускает награду; `untouched` не добавляет запас и отменяет удержанную выплату. Сверяйте игрока, заказ и сохранение перед решением. `paid/retry` для спорной банковской операции работают как прежде и не изменяют ресурсный запас.

## Обновление и миграция

1. Остановите сервер и сохраните резервную копию папок Towny/NeverLandTowny и данных игроков.
2. На комплекте 0.43.2 замените только JAR **Contracts** и **Control**. Уберите их предыдущие версии. Старые данные и конфигурации оставьте.
3. На более старом общем ядре используйте весь установленный совместимый комплект; неиспользуемые аддоны ставить не нужно.
4. Запустите сервер без `/reload`. Проверьте `/orders` и административный склад.

Каталог обновится до v4: добавятся новые шаблоны, а исходный `orders.yml` сохранится как `orders.pre-catalog-v4.yml`. Ваши лимиты (в том числе личные 5000), веса, размер доски, старые пользовательские задания и их условия сохраняются. Новые шаблоны попадут в следующую подборку в **00:00 МСК**. Сегодняшняя доска и уже принятые задания не перезаписываются.

Склад учитывает сдачи, выполненные новым механизмом после обновления, включая ранее принятые, но ещё не сданные заказы. Старые завершённые сдачи автоматически не восстанавливаются: прежний код не хранил ресурсный склад. Незавершённые старые квитанции сохраняют прежний путь выплаты и не создают выдуманные запасы задним числом.

Для резервного копирования остановите сервер и сохраняйте папку плагина целиком: SQLite-файл, `-wal`/`-shm`, если они остались, денежный журнал и файлы заказов. Для полного отката нужны соответствующие данные игроков. Не удаляйте отдельный журнал и не редактируйте таблицы вручную.

## API будущих строек

Через Bukkit ServicesManager зарегистрирован `ru.neverland.mintcontracts.api.ServerMaterialsApi` v1. Возможности: `balances`, `reserve`, `consume`, `release`. Методы возвращают `CompletionStage`; результаты состоят из неизменяемых стандартных типов Java. Не блокируйте потоки Folia ожиданием результата.

Будущий строительный плагин получает доступные остатки, резервирует всю стоимость под уникальным ID, строит в региональных планировщиках и затем подтверждает расход или возвращает неиспользованный резерв. Резерв нескольких материалов выполняется одной транзакцией: нехватка одного отменяет весь резерв. Один и тот же ID не может изменить проект, стоимость или автора и повторно списать запас.

## Проверка

Отчёты и ограничения — `docs/validation/server-materials-0.44.0/`. Проверки используют реальный SQLite, реальные файлы выплат и сбои на границах операций. Отдельный стенд Folia проверяет доступность встроенного драйвера, опубликованный API, сохранение остатков и прежние сценарии планировщика. Подключение клиента и ручная сдача каждого материала остаются отдельным плейтестом.
