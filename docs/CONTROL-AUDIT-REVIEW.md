# Проверка операций в Control 0.6.1

В `/nltadmin` → «Журналы операций» появилась кнопка «Проверка операций». Раздел показывает исходные квитанции и помогает выбрать операции для ручной сверки. Он не меняет деньги, ресурсы, наказания или состояние сделки.

Доступ: OP либо `neverlandtownycontrol.admin` и `neverlandtownycontrol.audit`. Право администратора включает аудит по прежней схеме наследования. Для экспорта отдельно требуется `neverlandtownycontrol.audit.export`. Права проверяются при переходе и при получении фонового результата. Ответ от закрытого или заменённого окна не открывает меню снова.

## Карточки

- **Проверить завершение операции.** Последняя найденная запись данного аддона, типа шага (`kind`) и ID операции имеет незавершённый/требующий сверки статус и старше 10 минут. Если последняя отметка содержит несколько статусов с одинаковым временем, они показываются вместе. В карточке указан проверяемый шаг. Запись другого аддона или другого типа шага с тем же ID не считается его завершением: например, `TRADE_PAYMENT / COMPLETED` продавцу не скрывает `CARAVAN_DEAL / PAYING`, пока не завершены остальные выплаты. Более поздняя конечная запись того же типа шага снимает соответствующую подсказку.
- **Быстрая передача через третий город.** Два подтверждённых `BANK_TRANSFER / COMPLETED` проходят через три разных города за 15 минут. Каждый перевод — от 1000 монет, разница сумм — не больше 10% первой суммы. Наблюдения отдельных списаний/зачислений, банковские команды и цены торговых сделок не добавляются как новые переводы.

Карточка означает только совпадение с правилом. Журнал может запаздывать, а законная торговля также может давать такую цепочку. Администратор открывает квитанции, копирует ID и сверяет текущее состояние в соответствующем аддоне. Автоматического повторения платежа или вывода о нарушении нет.

По умолчанию проверяется текущий календарный день Москвы. Кнопка периода переключает на семь календарных дней. Более старые записи остаются доступны через обычный поиск. Проверка ограничена 20 000 записями, 8 388 608 символами и 200 карточками; при превышении результат не показывается как полный. Для большого объёма используйте меньший период или точный поиск.

В подробностях любой записи есть «Связанные записи»: поиск по точному ID операции во всех аддонах. Само совпадение ID не означает повторную выплату. В карточке цепочки доступны обе исходные квитанции.

## Индекс и сверка

Исходные файлы `plugins/NeverLandTowny*/audit/YYYY-MM.tsv` остаются основными свидетельствами. В `plugins/NeverLandTownyControl/audit-index/derived-v1.sqlite` хранится только восстанавливаемый индекс поиска.

Неизменившиеся месячные файлы повторно не разбираются. При изменении файл проверяется по контрольным суммам до публикации нового снимка. Записи, дописанные после зафиксированного конца файла, попадут в следующий снимок. Повреждённый исходный файл отменяет запрос целиком, даже если повреждённая строка не относится к выбранному фильтру.

Команды:

```text
/nltaudit search id=<ID операции или квитанции>
/nltaudit search town=<UUID города> since=2026-10-01 until=2026-10-31
/nltaudit status
/nltaudit reindex
```

`status` полностью перечитывает исходные журналы и проверяет контрольные суммы, также показывает состояние банковской очереди. Это подходит для глубокой проверки после ручных действий с файлами: обычный поиск использует метаданные неизменившихся источников.

`reindex` удаляет только производный индекс и собирает его заново. Исходные TSV и журналы платежей не изменяются. Если повреждён исходный TSV, пересборка не скрывает ошибку: сначала необходимо восстановить этот файл из проверенной копии. Индекс не является резервной копией платежей.

Чтение выполняется вне общего состояния аддонов. Одновременно допускаются две проверки индекса; обработка соединений сериализована отдельной блокировкой фоновых исполнителей. Ограничения источников: 4096 файлов, 2 ГиБ суммарно, 512 МиБ на файл, 5 000 000 записей. Одна строка ограничена 2 097 152 символами, обновление и выборка — бюджетами по 30 секунд. Превышение приводит к явному отказу; файлы не обрезаются автоматически.

## Банковские наблюдения

`BANK_LEG`, `BANK_TRANSFER` и `BANK_COMMAND` теперь попадают в отдельную очередь записи. В момент наблюдения сохраняются неизменяемые стороны, названия, время и ID; исполнитель записи не обращается к Towny для повторного разрешения имён. Поэтому переименование города между событием и записью не переписывает историю.

Очередь допускает 512 ожидающих заданий и одно выполняемое, с общим пределом 4 194 304 символа. Описания банковских событий ограничиваются 4096 символами. При переполнении или ошибке файла появляется `AUDIT GAP`, а счётчик пропусков виден в `/nltaudit status`. Банковская операция не повторяется и не откатывается из-за сбоя журнала.

Штатная остановка дожидается принятых записей вне `SuiteState`, до пяти секунд. Если подтверждения за это время нет, выводится явная ошибка аудита. Неподтверждённая очередь не объявляется полным журналом платежей.

## Проверено

Нативный стенд: Folia 26.2 `14b7fee`, Towny 0.103.2.0, Java 25.0.5. Два последовательных JVM: **23 проверки первого запуска и 8 после полного рестарта**. Результаты и SHA-256 JAR: `docs/validation/city-systems-052/control-audit/native-results.json`.

Проверены настоящие меню и события клика, доступ по праву и OP, отзыв права, старое окно и поздний ответ; построение SQLite-индекса, поиск связанной операции, повреждение исходного TSV и индекса, восстановление через `reindex` и побайтовая неизменность источника при просмотре. Банковский исполнитель проверен с реально заблокированным `AuditJournal`, доступным глобальным `SuiteState`, настоящим переименованием города и принятым заданием, остающимся в очереди при входе в `Control.onDisable`. После рестарта сохранены точные ID и времена, без повтора квитанций.

Квитанции переводов/незавершённой сделки внесены явно как тестовые данные; настоящие деньги не перемещались. Игрок, его окно и EntityScheduler — офлайн-заменители, работающие через настоящий регион Folia. Отрисовка сетевого клиента и отдельная интеграция с LuckPerms этим стендом не заявляются. Изоляция ошибки Quests проверяется отдельным сценарием `QUESTS-FAILURE-ISOLATION.md`.

Изменение 0.6.1: успешная запись отдельного этапа не закрывает незавершённый этап другого типа. Карточки разделены по аддону, типу и ID операции; добавлена категория планов расширения и понятные названия этапов событий. Повторная нативная проверка 0.6.1: 23+8 PASS, обе JVM exit0. Новые четыре регрессионные проверки различения этапов проходят в AuditIndexSmoke (1043 проверки); доказательства новой сборки — validation/city-systems-052/control-audit-061.
