# Сезонные запасы и ярмарки

Версии: NeverLandTownySeasons **0.2.0**, NeverLandTownySpecialization **0.3.0**. Существующие сезонные коэффициенты, выбор специализации, производственные сметы и общие проекты сохраняются.

## Для игроков

- `/t seasons` — прежний календарь; кнопка «Сезонный запас и ярмарка» открывает новый раздел.
- `/tseasons stock` — свободная готовая продукция, резервы, фактический выпуск и полученные/переданные партии.
- `/tseasons fair` — входящие и исходящие предложения, история резервов и обменов.
- `/t specialization products` — выпуск готовых партий по существующим сметам из реально сданных материалов.

Жители могут просматривать запас своего города. Только действующий мэр с правом `neverlandtownyseasons.manage` подтверждает резерв или обмен. Перед подтверждением показаны названия обоих городов, точные товары и количества, срок по Москве. Кнопки ожидают сохранения и защищены от двойного нажатия. Выход из меню не отменяет уже принятую операцию; её результат можно проверить в истории.

«Подготовить запас» откладывает уже имеющиеся партии для следующего сезона. Другие сметы и ярмарка не могут потратить эти партии. Это организация городских запасов: новых бонусов, производства, предметов или денег подготовка не выдаёт. Резерв освобождается по указанному сроку либо по решению мэра/администратора, полностью и без штрафа.

Для обмена первый мэр выбирает соседний город того же мира и шаблон, проверяет условия и резервирует свой товар. Второй мэр открывает входящее предложение, видит эти же сохранённые условия и отдельно подтверждает. Только тогда обе стороны одновременно передают продукцию. Если встречного товара либо места не хватает, ничего не списывается и предложение остаётся ожидающим. Принятый обмен отменить нельзя: товары уже перешли между городами. Непринятое предложение отменяет его создатель или администратор; истёкшие предложения возвращают резерв автоматически.

Меняется учёт готовой продукции Specialization. Физические предметы из инвентаря/склада Builds здесь не перемещаются, баланс Towny/Vault не затрагивается. Выпуск продукции по-прежнему обеспечивается расходом материалов Contracts. При импорте `received` увеличивается, а `produced` остаётся реальным выпуском самого города.

## Общий календарь

Источник — существующий `SeasonService.calendar(world)`, для города используется мир домашнего участка. Второго счётчика сезонов нет. По умолчанию ярмарка открыта последние два дня сезона.

Для ручной фиксации и RealisticSeasons API сообщает сезон без номера дня. При `fair.allow-undated-source: true` ярмарка открыта весь сообщённый сезон; при `false` новые обмены ждут источник с датой. Изменение источника/сезона/года закрывает прежние предложения и возвращает исходный резерв. Возобновление сервера не приводит к автоматическому обмену.

Каждое предложение имеет конечный сохранённый срок: по умолчанию 2 часа, запас — 24 часа. При CUSTOM срок предложения дополнительно ограничен оставшимся временем текущего сезона, а запас — концом следующего. При MINECRAFT и внешнем/ручном источнике срок задаётся реальным временем; дата самого сезона продолжает поступать из исходного календаря. Остановка сервера не продлевает срок, а после запуска просроченный резерв возвращается владельцу без потерь.

## Установка и настройка

1. Остановите сервер и сохраните копии каталогов Seasons и Specialization, в том числе `production.sqlite`. Не копируйте работающий SQLite-файл отдельно от WAL.
2. Замените прежние JAR обоих аддонов, оставив по одному файлу каждого имени.
3. Запустите сервер. Новый `season-markets.yml` создаётся отдельно; прежние `config.yml`, `calendar.yml` и `specialization-data.yml` сохраняются.
4. Проверьте `/tseasons status`, `/tseasons stock`, производство и общий проект специализаций.

Seasons находит Specialization во время работы через API и не задаёт зависимость порядка загрузки: иначе в полном паке образуется цикл Seasons → Specialization → Power → Upkeep → Resources → Seasons. Поздний запуск или повторное появление провайдера подхватывается при следующем открытии/обновлении раздела. Без провайдера обычный календарь работает; новый раздел объясняет, почему готовая продукция недоступна. Отказ отдельного API/каталога изолирован. Полное административное отключение Seasons в большом паке дополнительно подчиняется графу Control: косвенные зависимости через Resources/Events/Upkeep могут остановить другие модули. Этот этап проверяет локальную изоляцию и убирает лишние прямые связи; оставшиеся косвенные зависимости требуют отдельной проверки. Неправильный `season-markets.yml` приостанавливает только новые сезонные операции. Старые подтверждённые предложения хранятся в провайдере; администратор может вернуть их резерв даже при неисправном сезонном каталоге.

`season-markets.yml`:

| Параметр | Значение по умолчанию | Ограничение |
| --- | ---: | --- |
| `enabled` | `true` | `false` блокирует новые резервы и обмены |
| `fair.last-days` | 2 | 1–365 |
| `fair.allow-undated-source` | `true` | Поведение источника без номера дня |
| `reserve-hours` | 24 | 1–168 |
| `offer-hours` | 2 | 1–24 |
| `plans` | Четыре сезонных плана | 1–7 товаров, 1–64 партии каждого, всего ≤128 |
| `exchanges` | Восемь шаблонов | 1–16 шаблонов, разные товары на двух сторонах |

Изменение шаблона влияет на новые сметы. Уже подтверждённая запись хранит собственные количества, названия, города, инициатора и срок. После изменения конфигурации выполните `/tseasons reload`; загрузка нового каталога происходит асинхронно. Неверная новая конфигурация не подменяется старыми условиями молча.

Права LuckPerms: `neverlandtownyseasons.use` — просмотр; `neverlandtownyseasons.manage` — подтверждение своим мэром. Оба по умолчанию доступны игрокам, но роль мэра дополнительно проверяется на сервере перед записью. `neverlandtownyseasons.admin` по умолчанию OP.

## Администрирование и доказательства операций

`/tseasons admin list`, `/tseasons admin status <UUID>`, `/tseasons admin cancel <UUID>`. Командный исполнитель предоставляет протокол административного меню v1, действия `status`/`cancel`; подключение кнопки в Control требует `activities: true` для Seasons. Запрос отмены сразу сообщает об ожидании записи, а успешный полный возврат — только после SQLite ACK.

Новые категории журнала: `CITY_SEASON_STOCK` и `CITY_SEASON_FAIR`; исходы `HELD`, `SWAPPED`, `CANCELLED`, `EXPIRED`. Запись содержит идентификатор операции, точного действовавшего мэра/администратора, города, товары, количества и основание. Обмен создаёт две записи направлений с одним идентификатором обмена. Журнал доставляется существующим асинхронным outbox: отказ аудита сохраняет недоставленные записи для повтора, не выполняет обмен ещё раз.

## Сохранение и границы

Единственный владелец состояния — `NeverLandTownySpecialization/production.sqlite`. Схема 2 добавляет `received`/`sent` и `seasonal_entries`. Миграция сохраняет прежние свободные/резервные/произведённые партии, включая полностью израсходованные строки; старые совместные резервы не доступны ярмарке. Схема1 → 2 выполняется транзакционно и повторно безопасно. Для отката на старый JAR требуется восстановить соответствующую копию БД при остановленном сервере; старый провайдер не должен читать новую схему как старую.

Каждая первая резервация и окончательный обмен выполняются в одной SQLite-транзакции; одна очередь на 128 работ, WAL/FULL, конечное ожидание блокировки. Перевод проверяет вместимость обоих городов с учётом обещанного незавершённого производства. Уникальны ID предложения и квитанция обмена. Чужая квитанция, иная смета и повтор завершённого обмена не могут создать товар. SQL-сбой откатывает обе стороны и закрывает новые операции провайдера до проверки, сохраняя прежние бонусы специализации.

Пределы нового журнала: 100 000 записей, 1 024 активных резерва на сервер, 8 у города, из них не более одного запаса подготовки. После заполнения новые сметы закрываются; уже принятые записи можно завершить/освободить. Каждая проверка сроков закрывает не более 50 записей, списки показываются страницами. Новая конфигурация читается отдельной ограниченной очередью; SQL и аудит не ждут диск под общей блокировкой Suite. Завершение отключения ждёт принятые записи вне Suite, затем закрывает аудит и БД.

Унаследованные `SeasonRepository`/основной reload календаря и reload старого производственного каталога по-прежнему содержат синхронное чтение/запись. Этот этап не заявляет перенос всего старого I/O на async. Новые данные ярмарки, резервов и конфигурации не добавляют синхронной записи под Suite.

## Проверки

Холодные программы: прежние SeasonClockSmoke/SeasonStorageSmoke и SpecializationSmoke/ProductionSmoke/ProductionAuditSmoke, новые SeasonMarketsSmoke (17 проверок) и ProfileGoodsSmoke (40 проверок). Последний использует реальный SQLite: физическую задержку writer-lock, два направления, квитанции, совместные резервы, ёмкость с обещанными партиями, откат при SQL trigger-failure, перезапуск, миграцию и outbox-направления/акторов, порядок публикации ACK-снимков.

Native fixture: `scripts/season-markets-runtime-probe`, отдельные строго последовательные JVM first/broken/restart. На свежем tmpfs-стенде одним foreground runner пройдены **35 + 16 + 17 = 68 проверок**, все три JVM завершились с exit 0. Между запусками проверены hash исходной БД и отсутствие WAL/SHM/journal; onLoad hash совпал до открытия провайдера. Прежняя аномалия overlay-стенда сохранена в отчёте: точная первопричина не установлена, чистый tmpfs-прогон не объявляется исправлением SQLite. Доказательства и точные hashes: `docs/validation/city-systems-052/season-markets/`, immutable manifest в каталоге probe. Проверены прежние native зависимости Contracts0.7.0/Builds0.10.1/Control0.6.0; совместимость всего нового полного пака проверяется отдельно. Это не утверждение проверки клиентского рендера или живого банковского платежа.
