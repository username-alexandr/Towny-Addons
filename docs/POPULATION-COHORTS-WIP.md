# Население по районам — незавершённый этап

Общий пункт Population в CITY-SYSTEMS-IMPLEMENTATION.md ещё **не выполнен**. В интерфейсе Population пока нет нового раздела.

## Уже подготовлено

- DistrictCohorts — чистая модель виртуальных групп по месту жилья, отдельно от расположения рабочих мест. Существующее общее население, трудоспособность и городская занятость распределяются без добавления людей. Подгруппы: работающие, ищущие работу, остальные жители.
- Не распределённая по районам/базовая часть остаётся в отдельной группе; она не объявляется бездомными. Переполнение жилья не удаляет жителей. Глобальный предел вместимости распределяется пропорционально; неизвестная добавочная вместимость остаётся общегородской.
- Еда/вода — точные BigDecimal-единицы прежнего городского снабжения и спроса. Это декомпозиция существующих значений, без второго расхода ресурсов и без изменения роста/убыли.
- Целочисленное распределение по наибольшему остатку с устойчивой очередностью ключей; BigInteger исключает переполнение произведения количества на вес. Неизвестные местные службы остаются неизвестными.
- DistrictCohortsSmoke: 22 проверки и 10000 случайных распределений с проверкой всех городских итогов.
- Общий DerivedViewCache вынесен из проверенного DistrictPlanner: неизменяемые данные, один CPU-исполнитель, очередь 16, кеш 128, один незавершённый запрос на город, явное ожидание/ошибка и отмена только производных расчётов при остановке. Нельзя использовать для платежей/принятых вкладов.
- Districts 0.2.1 отдаёт согласованный `assessment` формата 2 с `assignments`: физическое соответствие всей принадлежащей городу площадки району. Это не карта бонусов; учитывает и низкие текущие уровни. Population должен требовать готовый формат 2. Невалидная/пересекающая два района площадка не должна молча распределять людей.

## Следующая реализация

1. Сначала перевести PopulationRepository на AcknowledgedState с прежней схемой 1. Последние подтверждённые N/остаток/история/время — единственный источник API. Собрать весь городской цикл в один кандидат Map, публиковать новый результат только после подтверждения файла. Запуск и административное назначение также асинхронные. Ошибка записи останавливает изменение населения, сохраняет подтверждённые данные, не превращается в убыль.
2. Убрать запись из просмотров. Периодический pulse готовит кандидат и очищает удалённые города; refresh(false) только строит кеш по подтверждённым данным. Rebase на старте должен закончиться до первого advance, чтобы не было офлайн-роста/убыли. Во время занятого писателя новый цикл не запускается. По подтверждению пересчитать кеш без advance. Закрытие — ModuleShutdown, дождаться вне SuiteState. Старые тесты репозитория перевести на async commit; добавить реальные задержку/ошибку файла.
3. Общая формула Capacity и покомпонентные источники должны совпадать. Захватывать per-building Capacity из той же арифметики, которая строит итог города; не вызывать живые множители второй раз при просмотре. Food/water для групп брать из итоговой Capacity после ограничения стратегическим снабжением.
4. Строгий мост Districts.assessment: готовность, format=2, rows, assignments, даты и отдельные known. Нет Districts — одна общегородская группа; установленный, но недоступный источник — явное ожидание/недоступность только нового раздела, без влияния на старую симуляцию.
5. В PopulationService публиковать неизменяемые входы для производных групп. API cohorts должен читать кеш/DerivedViewCache, не обращаться к Towny/Bukkit из асинхронного интеграционного вызова. Интерес к городам ограничить 128 с истечением, чтобы не считать все города без зрителей.
6. Добавить адресный refreshTownView(UUID), чтобы новый экран не пересчитывал все города при каждом нажатии. Старый refreshView сохранить для совместимости. Один источник Capacity, старые параметры роста/лимиты сохранены.
7. Меню/команда cohorts: виртуальные жители/жильё; городская занятость живущих здесь — отдельно от рабочих мест района; точные спрос/доли общегородского снабжения; местная доступность служб и связь; понятная общегородская группа; одна кнопка в основном меню, обычные back/refresh/page. Проверять право use и свой город/администратора. При ожидании ограниченно обновлять то же окно по EntityScheduler, не переоткрывать заменённое окно.
8. Новый config cohorts.enabled; сбой/выключение раздела не меняет N, старые правила, снабжение или сохранённые данные. Перезагрузка должна обновить getConfig, старый reloadPopulation пока этого не делает.
9. Native Folia: реальный Population/Builds/Districts; сохранённые жилые/промышленные площадки — явная fixture; одно N, точные суммы групп, отсутствие второго расхода, временно недоступные источники, настоящая задержка population-data.yml и полное восстановление после рестарта. Игрок/окно/планировщик подменены явно, не заявлять проверку клиента/банка.

Репозиторий до миграции: put/retain/rebase/save синхронные. Прямых вызовов PopulationService.setPopulation из старых Java-проб не найдено; команда — основной вызывающий. PopulationSmoke.persistence использует put/save/rebase/retain, потребуется сохранить смысл проверок на новом async API.
