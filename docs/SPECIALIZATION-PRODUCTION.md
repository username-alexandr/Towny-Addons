# Производственные партии и общие проекты городов

NeverLandTownySpecialization 0.2.0 добавляет городской каталог готовой продукции и совместные цели нескольких направлений. Прежний выбор специализации, бонусы, уникальные здания и склады Builds/Resources сохраняются. Для новых партий нужен Contracts 0.7.0 с подтверждёнными поставками `/orders`.

## Как пользоваться

1. Мэр открывает `/t specialization products` → «Начать производство». Для выпуска нужна специализация выбранного рецепта и работающее уникальное здание III уровня или выше.
2. После просмотра материалов и подтверждения создаётся отдельная смета. Сразу продукция не выдаётся.
3. Любой житель открывает эту смету, выбирает свой уже принятый заказ **доставки** из `/orders` и подтверждает передачу. Действуют прежняя личная награда и прежние лимиты заказа. Добыча, охота и рыбалка материалы не передают.
4. Недостающие материалы резервируются для сметы; излишки остаются в запасе сервера. Если смета успела закрыться, вся поставка пополняет запас сервера, а награда исходного заказа сохраняется.
5. Когда смета обеспечена, мэр подтверждает выпуск. Только подтверждённое использование всей сметы создаёт точное количество партий в городском каталоге.
6. В «Совместных проектах» мэр выбирает общую цель. Города разных направлений вносят уже выпущенные партии в её резерв. После полного обеспечения мэр города-организатора завершает проект.

**Производственная партия учитывается в каталоге города. Предмет в личный инвентарь не выдаётся.** Она предназначена для совместных целей; этот выпуск не создаёт денег, обычных ресурсов, новых бонусов или автоматически построенного здания. Завершённая общая цель сохраняется в списке проектов вместе с результатом, городами, участниками и квитанциями. Предусмотрены выставка городских мастеров, смотр общего снабжения и праздник содружества.

Один город представляет в конкретном проекте одно направление. Смена специализации не позволяет тому же городу заменить второго участника. Старые партии сохраняются после смены направления; внести их можно, когда город снова имеет нужную специализацию.

## Команды и права

| Команда | Назначение |
| --- | --- |
| `/t specialization products` | Каталог городских партий |
| `/t specialization batches` | Производственные сметы своего города |
| `/t specialization produce <товар> [число]` | Просмотр и подтверждение рецепта для нескольких партий |
| `/t specialization batch <UUID>` | Открыть сохранённую смету |
| `/t specialization cooperation` | Общие проекты городов |
| `/t specialization project <UUID>` | Условия, участники и результат общего проекта |
| `/townyspecialization reload` | Перечитать настройки |

Все формы `/t specialization ...` доступны также как `/townyspecialization ...`. Для чтения меню нужно `neverlandtownyspecialization.use` (по умолчанию есть у игроков). Создание, выпуск, отмена, передача партий и завершение общей цели дополнительно проверяют **актуальное мэрство своего города**. Право `manage`, совет, OP и старое административное право выбора специализации не подменяют это требование для новых производственных действий. После отложенного ответа склада мэрство проверяется снова. Смена города, утрата прав или выход прекращают дальнейшую неподтверждённую операцию; сохранённую смету новый мэр может сверить позже.

`neverlandtownyspecialization.admin` по-прежнему позволяет перечитать настройки и управлять прежней специализацией. Для самих заказов нужно обычное `neverland.orders.use`.

## Рецепты и пределы

Новый файл `plugins/NeverLandTownySpecialization/production.yml` содержит отдельный переключатель `enabled`, рецепты `products`, общие цели `projects` и пределы `limits`.

| Направление | Партия | Материалы на одну партию |
| --- | --- | --- |
| Торговое | Торговые комплекты | 64 бумаги, 32 стекла |
| Крепость | Оборонные комплекты | 64 железных слитка, 64 дубовых бревна |
| Сельскохозяйственное | Продовольственные партии | 128 пшеницы, 64 моркови |
| Промышленное | Промышленные узлы | 64 железных слитка, 128 камня |
| Научное | Исследовательские комплекты | 128 бумаги, 64 стекла |
| Портовое | Портовое оснащение | 128 дубовых брёвен, 64 белой шерсти |
| Религиозное | Праздничные комплекты | 64 белой шерсти, 32 кварцевых блока |

По умолчанию: 3 незавершённых сметы на город / 200 на сервер; до 8 партий за одну смету; 128 свободных, зарезервированных и уже обещанных партий на город / 20 000 на сервер; 3 открытые общие цели организатора / 100 на сервер. Незавершённые сметы занимают будущую вместимость до выпуска или отмены, поэтому параллельные подтверждения не обходят предел.

Начатые сметы сохраняют точный рецепт, название, направление и количество. Общая цель сохраняет свои требования и текст результата. Изменение конфигурации влияет на новые подтверждения. Уже зарегистрированный идентификатор продукции нельзя переназначить другому направлению: создайте новый ID.

`enabled: false` блокирует новые сметы и общие цели. Просмотр, сверка, безопасная отмена и завершение ранее принятых операций остаются доступными. Ошибка именно `production.yml` закрывает новые рецепты, сохраняя прежнюю специализацию и доступ к сохранённому учёту. Ошибка `production.sqlite` блокирует изменения нового раздела; прежняя система специализаций продолжает работать. Ошибка/отключение Contracts оставляет незавершённые сметы на сверку; она не выдаёт партии без подтверждения.

## Отмена и сверка

Отмена производственной сметы возвращает её неиспользованный резерв **в запас сервера**. За эти материалы игрок уже получает обычную награду `/orders`, поэтому повторного возврата предметов в инвентарь нет. Выпущенную партию отменить нельзя.

Отмена общего проекта возвращает ранее зарезервированные партии **каждому исходному городу**, ровно один раз. Завершение расходует резерв и сохраняет памятный результат; завершённую цель нельзя затем отменить и вернуть расход.

Кнопка «Сверить состояние» запрашивает существующую квитанцию Contracts. После рестарта подтверждённый расход выдаёт только недостающую локальную партию, а повторная проверка не выпускает её снова. Не удаляйте зависшую смету или запись в БД вручную: при несовпадающей квитанции выдача намеренно остановлена для проверки.

## Хранение, журнал и обновление

Отдельный `production.sqlite` хранит сметы, свободные/зарезервированные/выпущенные партии, замороженные условия целей, вклады и историю. Изменение баланса и квитанция выполняются одной SQLite-транзакцией. Один ID сметы связан с одним ID материала Contracts (`batch_...`) и одним выпуском; другая, уже использованная квитанция не подходит. Работа выполняется на ограниченном SQL-потоке, без ожидания диска в Folia-потоках. Штатная остановка дожидается принятых операций и проверяет закрытие WAL.

Все изменения попадают в местную историю и в административную категорию `CITY_PROJECT`. Сначала подтверждается квитанция в БД; затем отдельный поток отправляет её в общий журнал с неизменными ID и временем. Неподтверждённая запись остаётся в БД для повторной отправки после запуска. Повтор аудита не повторяет выдачу или возврат партий. Участники получают записи завершения/отмены общей цели в истории своих городов.

Перед обновлением остановите сервер и сохраните полные каталоги Specialization и Contracts вместе с файлами SQLite/WAL, если они присутствуют. Замените старый JAR Specialization одной версией 0.2.0; Contracts должен быть не старее совместимой 0.7.0. Прежние `config.yml`, `specializations.yml` и `specialization-data.yml` не удаляются. Новый конфиг создаётся отдельно. Для отката нужна согласованная резервная копия обоих аддонов: они совместно учитывают уже использованные материалы.

Прежний репозиторий выбора специализации ещё использует старое синхронное сохранение. Новый раздел не переводит его и другие аддоны на SQLite; общий этап миграции остаётся отдельным.

## Проверки

Холодная сборка на pinned Folia API и JDK25: прежняя проверка специализаций плюс 32 проверки реального SQLite-учёта и 7 проверок административной проекции. Проверяются чужая/неполная квитанция, однократный выпуск, резерв, многогородское участие, отмена, пределы, реальная SQL-ошибка между начислением и сменой статуса, рестарт, отказ аудита и отсутствие блокировки Suite/SQL-потока при задержке журнального файла.

Нативный прогон Folia 26.2: **47 проверок на трёх отдельных JVM (20 + 14 + 13)**. Проверены реальные API Contracts/Specialization, расход подтверждённых материалов, смена мэра перед ответом склада, однократная сверка незавершённого выпуска после рестарта, отмена/завершение общих целей, административный журнал и изоляция повреждённого `production.yml`. Все выходы имеют код 0; после каждого выхода нет WAL/SHM, хеши основных баз совпадают перед следующим запуском. Результаты и точные хеши: `docs/validation/city-systems-052/specialization-production/` и `scripts/specialization-production-runtime-probe/validated-0.2.0.json`.

В стенде используются явно заданные офлайн-игроки/окна/планировщики, подтверждённые поставки материалов и кеш работающего уникального здания III уровня. Это не проверка сетевого отображения Minecraft-клиента, реального строительства уникального здания или банковского провайдера. Ранее наблюдавшаяся аномалия появления старого WAL между tool-вызовами сохранена отдельно; её причина не установлена, в финальном полностью foreground прогоне она не повторилась.

## 0.3.0: обеспеченный сезонный обмен

Схема `production.sqlite` 2 добавляет атомарные обмены и сезонные резервы через `ProfileGoodsApi` v1. Совместные проекты, их резервные партии, подтверждение расхода Contracts и первоначальные бонусы специализации сохраняются. Счётчики `received`/`sent` отражают межгородской обмен; `produced` остаётся историей собственного производства. Подробности, команды, ограничения, миграция и границы проверок: [SEASONAL-STOCK-FAIRS.md](SEASONAL-STOCK-FAIRS.md).
